THOMAS · Architect MUDServer & Database Efficiency Review

How a 15,781-room living world with weather, power, traffic, AI and 130 plugins runs on a free Render dyno and a Neon compute that is asleep most of the time — what is left to do, and where the ceiling actually is. updated 2026-08-16

§ 0The shape of the problem

Everything below follows from one fact, so it is worth stating before any of the cleverness.

Prod Postgres is somewhere else. Neon is a remote managed database, so every query() is a pool checkout plus a network round trip — tens of milliseconds, whether it reads one row or a thousand. The bill and the lag are both driven by round-trip count, not query cost.

That single observation reframes the whole design. The question stops being "is this query fast?" and becomes "does this need to be a query at all?" — and the answer, on almost every hot path in the game, turns out to be no.

§ 1What we do well

Five decisions carry essentially all of the efficiency. Each is a rule with teeth, not a habit.

1 · RAM is the world; the DB is the log

Boot reads the world once — zones, NPCs, furniture, doors, orgs, apartments, connections, regions, maps — into Maps in world.js. After that a room render is a Set lookup, not a query. Describing a room in a 15,781-zone world costs the same as describing one in a ten-room world.

The rule that makes this safe is written down and enforced: a cache is only as safe as its write funnel. furniture and npcs each had to earn their funnel first — roughly 40 scattered furniture writers were routed through insertFurniture/updateFurniture/deleteFurniture before the per-move furniture read could move off the DB, and bulk writers hand their SQL to updateFurnitureWhere, which appends RETURNING and re-caches exactly the rows Postgres says it touched — rather than re-implementing the WHERE clause in JS, which would be a second source of truth for the predicate.

2 · Every value has a declared read tier

Not "cache it if it feels slow" — a five-rung ladder, and every content table's tier is machine-readable in content-registry.js, with regress failing a table that hasn't declared one.

TierWhat lives thereWhy it's allowed to
boot Mapzones, npcs, doors, furniture, orgsevery writer funnels through one helper that updates Map + DB together
write-throughitem templates, world flags, skill IPall writers live inside the one module that owns the cache
event-bust + TTLcarried weight, equipped weaponmain paths emit a bust; a 5 s TTL covers the rest; staleness is benign
TTL contentquest definitions (30 s)authored, static at runtime; dev CRUD invalidates
query freshwanted/heat, security devices, generatorsuncoordinated writers — a stale answer would be worse than a round trip

The bottom rung is the interesting one. Choosing not to cache is a documented decision here, with a reason attached, which is why the caches that do exist can be trusted.

3 · Coalesced writes — the round-trip count stops tracking the player count

The three highest-frequency writes in any MUD are position (per step), combat HP (per swing) and survival resources (per tick). None of them issues a round trip at the mutation site. The mutation sets a dirty flag; a low-frequency flush persists every dirty player in one UPDATE … FROM (VALUES …).

The cost of the pattern is discipline, and a violation fails silently — no error, just an un-persisted change. So the invariants are written into the architecture doc as numbered rules: set the flag at every mutation site; never mutate a coalesced field after its flush in the same tick; write through and clear the flag on death and logout; drop a mid-loop write-through from that cycle's batch; offline players are DB rows and keep direct writes.

There is deliberately no generic dirty-flag framework and no shutdown flush. Instead every checkpoint field must be crash-benign by construction — restored slightly stale in a direction that doesn't reward crashing. Money, inventory, deaths and kills stay durable write-through, so none of the interesting state carries crash exposure.

4 · Nothing ticks on an empty world

This is the one that turns architecture into money. Neon suspends an idle compute after ~5 minutes and stops billing. A single recurring tick that awaits a query inside that idle window keeps a connection alive and pins the compute awake — the server then bills 24/7 for nobody.

So scheduler.js idle-gates by default: every registered callback simply doesn't fire when hasActivePlayers() is false, and running-while-empty is the deliberate opt-in. That inverts the old convention where an author had to remember the guard — and one forgotten guard (a surveillance camera refresh) is exactly what pinned the compute once.

The keepalive ping follows the same logic from the other side: it hits /health, which is memory-only, so it holds Render awake without ever waking Neon — and it is itself idle-gated, because ungated it spent ~730 of the workspace's 750 monthly instance-hours holding up a process that had nothing to do.

5 · The batching rules are specific enough to follow

Generic advice ("avoid N+1") doesn't survive contact with 130 plugins. These do, because each names the actual bug that produced it:

  • Never query inside a loop — including looping over players. A per-minute tick calling a single-player helper for each live player costs one round trip per player per tick whether or not that player owns anything relevant. Two engine helpers exist so nobody hand-rolls it: resolveInventoryForPlayers(ids) and patchInventoryCustomData([...]). Measured: clothing-wetness and flashlight were ~6 round trips per player per minute between them — and the former sits inside the awaited tick.minute hook, so at 50 players those serial waits stalled radiation and drug decay behind them while holding a pool slot.
  • Resolve a shared value once per tick, not once per player. resourceTick called getEnvironmentState() per player to read one string — and that spreads getPowerMap(), which allocates an object per power-model zone. A 50-player world rebuilt a thousands-of-zones map fifty times a minute for one field.
  • A write that changes nothing is still a round trip. Diff-gate recurring bulk updates (IS DISTINCT FROM, or a last-saved stamp) so a stable world writes nothing — but keep the comparison to state you own, which is why player-flag writes are deliberately not coalesced.
  • Narrow the column list on wide tables. items/npcs/zones carry fat JSONB and audio_samples.data is base64 audio. Repeated SELECT * here is how the Neon egress budget died once already.
  • Independent reads issue together (Promise.all — describeZone's 4-way batch), same-row writes coalesce into one UPDATE.

Bonus: the parts that could have been expensive and aren't

  • No build step, no framework. 215 client JS files ship as-is; the only gate is a ~2 s parse smoke that catches the backtick-in-a-template-literal bug that once killed the entire client boot on prod.
  • No ORM. 2,922 call sites, one query() helper, plain parameterized SQL. There is no query builder generating something surprising at 3am.
  • No startup migrations. Boot touches neither schema nor content, so a restart costs a read of the world and nothing else.
  • The loose setIntervals are session-scoped, not clock ticks. The trip transform, MIS event loop, card-table shuffle SFX and dreamscape beat all bypass the scheduler — correctly: they exist only while a specific player is doing a specific thing, they self-cancel, and several defensively self-cancel again if the player vanishes. None of them can run on an empty world.
  • Content is git, not a live editing surface. 37,184 JSON files deploy through CI, so prod content changes cost a push — not a migration, not a boot-time rewrite.

§ 3Where the cost actually is

Idle traffic measured 45 → 112 → 163 round trips/min at 1 / 5 / 20 synthetic players. The number that matters is the slope, not the total: ~6 round trips per player per minute, on top of a ~40/min world floor.

§ 4What's left

Four open items. The first three are ordinary maintenance; the fourth is structural, and it is what the next section is about.

backlog 1 · 67 advisory lint findings, and the shape of the tail

npm run db:query-lint -- --all lists them. They are not distributed evenly: 28 sit in broadcast, 7 in zone-validator, 7 in tablet, and the rest is a long thin tail of one or two per plugin.

Why it matters, honestly: less than the number suggests. What remains is dominated by map-derivation sweeps, studio-wiring routes and dev-panel CRUD — cold paths run by an admin, where a round trip is the correct price. The work is triage, not conversion: walk the list, fix anything on a player path, and mark the rest query-lint-ok with a reason so the number means something. A backlog nobody has read is indistinguishable from a backlog of bugs.

use it 2 · The meter exists; nothing watches it yet

DB/min ships on the dev-panel World State monitor, coloured by per-player slope. But nobody has looked at it under real concurrent load, and there is no alert, no record, and no baseline written down anywhere but this page.

Why it matters: the point of a standing meter is to make a regression visible without a profiling session — which only pays off if somebody reads it at a moment that matters, i.e. with players online. Next step: capture the number at a busy moment, write it beside the ~40/min idle floor as the baseline, and pick the threshold that means "something new is per-player".

unknown 3 · WebSocket behaviour under concurrency has never been tested

Rate limiting, backpressure and broadcast fan-out past a handful of simultaneous connections are all untested. The architecture doc has said so since it was written.

Why it matters: every measurement on this page is about the database, and the database is no longer what breaks first. Outbound bytes per zone-event × players in that zone is the number nobody has. Next step: the recipe already exists — pass a counting function to startGameLoop() and messaging.setBroadcast(), sum Buffer.byteLength bucketed by payload type.

structural 4 · One process owns the world, and that is the ceiling

Everything that makes this cheap — the boot-loaded Maps, RAM-authoritative player state, coalesced flushes — assumes a single Node process is the authority. That is the right call and it is why the hosting bill is what it is. But scaling out is not a config change; it is a decision with a redesign attached.

Why it matters: the honest version of the story is "extremely cheap up to one box, then a decision" — and nobody has established where that box's limit is, so the decision has no trigger.

§ 5How this scales

The database was the bottleneck everyone assumed, and it measurably isn't. So the useful question changes: as players arrive, what actually breaks first?

The four ceilings, and which one you hit

Four resources can run out. They don't run out together, and the design has pushed one of them so far away that it is no longer the one to watch.

ResourceHow it scales with playersStatus
DB round tripsFlat. Measured 46/min at 1 player and 42/min at 20 — coalesced flushes grow the payload, not the trip countengineered away
Process RAMNearly flat. The world (15,781 zones + npcs + furniture) is a fixed cost paid once at boot; a live player is a small objectnot the limit
Tick CPULinear, on ONE core. Node is single-threaded — the 1 s combat tick and the per-minute sweeps walk live players, and nothing runs in parallel with themuntested
Socket bytesWorse than linear in a crowd. A zone event is serialised per recipient, so N players in one room is N sends of one payloadunmeasured
Pool slotsFixed at 10, deliberately. Contention is about tick convoys, not headcount — which is why the scheduler jitters phase and spreads subscribershandled

The crowd problem, which is the interesting one

Player count is not really the variable. Players per zone is. Two hundred people spread across the Basin cost almost nothing extra; two hundred people in one bar is a different program — every say, every emote, every swing fans out to everyone present, serialised once per recipient.

The path past one box — shorter than it looks

The open architecture question has always been phrased as "should the world cache move to Redis?" That understates how well this design happens to sit for sharding, almost by accident:

Three things make that shape workable rather than aspirational — and none of them was built for it:

  • The durable tier is already shared and already correct. Money, inventory, deaths and kills write through to Postgres at the mutation site today. Two processes doing that is not a new correctness problem; it is the existing one.
  • Cross-region travel is already a seam, not a step. Void travel made leaving a region an explicit transition with its own code path — a shard handoff has an obvious place to live.
  • Plugins are already per-process by construction. A plugin holds RAM state and registers ticks; nothing in the loader assumes it is the only copy running.

What would genuinely have to change are the global systems that assume one process sees everyone: broadcast channels, chat/radio, wanted and heat, corp influence, and anything walking world.players expecting the full roster. That list is the real cost of the move, and writing it out properly is the first day's work whenever the day comes.

The one-line version. The DB tier has been engineered out of the way and can be left alone. The next constraint is a single event loop and per-recipient broadcast fan-out — neither of which anybody has measured. Measure those two before writing a line of scaling code; and when the day comes, shard by region, because the design has quietly been shaped for it the whole time.
