▚ What changed

The Relay is retired (pending your cutover, below). db/seed.sql and db/audio-seed.sql — the monolithic dumps you and John kept overwriting each other with — are dead men walking. In their place:

  • One JSON file per world entity — content/npcs/mira_the_fence.json, content/zones/zone_rustpick_alley.json. You edit an NPC, git shows exactly that NPC changed. You both edit different NPCs, git merges silently. You both edit the same NPC, git raises a conflict instead of eating someone's work.
  • One registry to rule every table — server/models/content-registry.js declares every table content / runtime / player. The "scavenging tables missed the backup" and "flight missed the seeder" bug class is now a red regress build instead of silent data loss. Your regress suite enforces it (layer 1a).
  • Production updates itself. A GitHub Action deploys content on every push to main: regress on a throwaway world built purely from files → pg_dump backup → drift report → import. Nobody "forgets to run the script on live" ever again, because nobody runs it. And prod's dev panel becomes read-only for content — still fully live for ops (players, weather, power, spawns).
  • Deletions are surgical. Rows die only when their file dies in committed history. Player furniture, tapes, keycards, junction boxes — rows born at runtime never had files and can never be touched. And git revert of a bad content commit is a complete rollback: values restore, added rows delete, deleted rows resurrect. Verified by drill.

Then, the cutover — this is yours, Dave. You own regress and Supabase, so you perform the rites. The full runbook lives in docs/content-pipeline.md (bottom section). The shape of it:

  1. Freeze. Both of you stop content edits. Run the OLD pipeline end-to-end one final time (publish + Relay deploy) so prod ≈ seed ≈ both locals. The Relay's last act.
  2. Baseline. On a branch: node scripts/content/export.mjs --prod --yes — the file tree is born from production, the live truth.
  3. Reconcile. You and John each run npm run content:status against the branch. Its output IS the reconcile report: every row only in your DB is unpublished WIP — keep it (export + commit) or kill it. No silent losses; every divergence gets a decision.
  4. Merge to main. Both pull. The hook imports. Markers set themselves.
  5. CI secrets + rehearsal. In GitHub repo settings add PROD_DATABASE_URL — the Supabase session-mode string, port 5432, NOT the transaction pooler (pg_dump and deferred constraints need session mode) — and RENDER_DEPLOY_HOOK_URL (Render → Settings → Deploy Hook). Restore the latest prod pg_dump into a scratch DB, point the secret at it, run the deploy-content workflow by hand (Actions → Run workflow). Green? Drift ≈ 0? Counts sane? Point the secret at real prod, dispatch once more.
  6. Throw the switches. Uncomment the push: trigger in .github/workflows/deploy-content.yml. Uncomment CONTENT_READONLY in render.yaml (or set it in the Render dashboard). Then git rm the old machinery: relay-server, content-publish/sync, export-seed, setup-local-db, deploy-content-to-prod, the content-pull/diff/merge scripts, both seed files, the relay docs. backup-prod.mjs and db:restore survive — the escape hatches remain.

▚ Your commands

commandwhat it doeswhen
npm run content:export Your local DB → content/ files. Canonical serialization; rows that vanished locally delete their files (that's how deletions enter git). End of every design session, before you commit.
npm run content:import Files → your local DB. Applies SCHEMA_SQL first, then upserts + git-driven deletions, all in one transaction. Never drops the DB; your character survives. Rarely by hand — the post-merge hook runs it for you on pull. Manually after resolving a conflict, or --dry-run to preview.
npm run content:status Diffs your DB against the files. Exit 1 = you have unexported work. Before pulling, before walking away, whenever you're unsure. The seatbelt.
npm run content:lint Validates every file with no DB: JSON, real columns, no runtime columns, dangling FK refs that would break a fresh world. The pre-push hook runs it for you; run it by hand after gnarly merges.
npm run test:regress Your gate, as ever — now also verifies the registry classification and the prod read-only gate. CI runs it against a world built purely from files. Before code pushes (pre-push hook does it); content-only pushes skip it locally because CI regresses the merged main.
npm run db:schema Applies SCHEMA_SQL to your local DB. (content:import does this too.) After pulling a schema change, or standing up a fresh machine.

Fresh machine, someday: npm run db:schema + npm run content:import. That's the whole world, from nothing. No seed file, no wipe, no re-registering characters.

▚ A push that changes the schema

# Your new system needs a table (or a column).
1. Edit SCHEMA_SQL in server/models/schema.js   # idempotent DDL, as always
2. Classify the table in server/models/content-registry.js
   # content|runtime|player + pk — regress is RED until you do. This is
   # deliberate. This is the fix for flight-never-made-the-seeder.
3. npm run db:schema                            # apply locally
4. build your content in the dev panel / seed script
5. npm run content:export && npm run test:regress
6. commit code + schema + registry + content in one commit, push
# CI applies SCHEMA_SQL to prod before importing rows — the schema and the
# content that needs it travel together. "Nobody ran it on live" is extinct.

▚ Pushing to production — read twice

After cutover, pushing to main IS deploying to production. Code goes via Render, content via the CI workflow, same push. There is no separate deploy button because the button was the part humans kept forgetting.

  • Watch the Action once in a while. The drift report step names any prod rows that differ from files — that's someone's manual prod edit about to be overwritten. If it's ever non-zero and you don't know why, stop and ask before the next push.
  • Deletions are loud. The deploy log prints every row it deletes and the commit that killed its file. Skim it. If it's deleting something you didn't intend, git revert + push restores it — the pipeline is its own rollback.
  • Catastrophe: every deploy uploads a full pg_dump artifact first (14-day retention). psql -f it back. You will probably never need it. It exists so you can sleep.
  • Never hand-edit content on prod "just this once." The gate will refuse you over HTTP, and the drift report will tattle if you sneak past it with SQL. If a live fix is urgent: fix locally, push — it's live in minutes.

▚ Pulling John's work

git pull
# 📦 Content files changed in that pull — importing into your local DB…
# the post-merge hook imports automatically. You're done. Go build.

The only wrinkle: if John changed an entity you also edited locally but haven't exported, the import aborts on purpose and names the entity. Nothing is lost — your DB keeps your version. Then:

npm run content:export     # your edit becomes a file
git diff content/          # see both versions; resolve like any git conflict
git add content/ && git commit
npm run content:import     # now the world and the files agree

When the JSON gets fiddly: pick either side, import, re-make your change in the dev panel, re-export. The panel is still your workshop — git is just the vault.
