🩸 Egress, lanes & prod — the whole map, for Akerson

Bytes want to wander — keep the world home on your disk, push out when it's ripe
The 30-second version: Our Supabase bill blew past 5 GB of egress (data Supabase sends out). The fix: do all daily work against a local database, share our work over GitHub (free), and only touch the live Supabase DB on purpose — a real deploy. That's already set up. This page is so you don't accidentally undo it.

1 · What egress actually is

Egress = every byte the Supabase database sends back over the wire. Reads are what cost — a query returns rows, those bytes count. The 5 GB got eaten because something was reading from Supabase all day long (a dev server or the regress suite pointed at it). The whole strategy below exists to stop that.

The one setting that matters: in .env, DATABASE_URL must point at localhost — your own Postgres. It already does. If you ever change it to the Supabase pooler URL "just to test against real data," that's how the 5 GB comes back. Don't.

2 · Two lanes — how you & Cyd stay in sync

Everything we build travels over GitHub (basically free), never Supabase. But it goes by two different doors, and it helps to keep them straight:

🌍 World lane — content

Anything you make in the dev panel: zones, items, NPCs, enemies, furniture, drugs, recipes, VINE graphs.

It lives as rows in the database. You share it with Relay's ⇧ Publish content, which bundles it into db/seed.sql and pushes that one file.

Cyd gets it with ⇩ Sync content.

⌨ Code lane — files

Anything that's a file in the repo: the engine (server/), plugins, the client, docs, scripts.

You share it with plain git push. The pre-push hook runs the regress gate and blocks a red push.

Cyd gets it with git pull (or Relay's Sync, which pulls too).

Rule of thumb: built it in a file → git push.   built it in the dev panel → Publish content.

Common case: a new feature is usually both — push the plugin/engine code first (so the behaviour exists), then Publish the content it uses (the items/NPCs that rely on it).

3 · "Does pushing more often cost egress?" — No

  • git push goes to GitHub, not Supabase. It doesn't touch the 5 GB quota at all. Push once or fifty times — same zero.
  • git doesn't re-send the whole repo. Each push is just the new commits' delta. Five small pushes ≠ five copies of everything.

So push freely and often. Small green pushes are better than big risky ones. Your Supabase egress doesn't care about git.

4 · Production — three roads, and the one trap

Daily work is local. Every so often we push a finished, tested chunk live to the real Supabase DB so players see it. The catch: three different things can reach production, and they travel by three different roads. Get them out of sync and prod breaks.

WhatHow it reaches prod
Codeengine / plugins / client git → the live host pulls & restarts separate step
Content rowsthe dev-panel tables Relay ⇧ Deploy content → Production (only ever adds) one button
Schema shapea new column / table a manual one-shot ALTER / npm run db:schema on prod NOT automatic
The trap (this answers "won't new code break?"): our schema DDL is all CREATE TABLE IF NOT EXISTS — it happily creates a brand-new table on prod, but it never adds a new column to a table that already exists. So:
  • New code that writes to a new table → fine, the content deploy creates it.
  • New code that writes to a new column on an old table → crashes on prod ("column does not exist") until you run the ALTER by hand.
  • New code that references content you haven't deployed (an item, NPC, zone) → runs, but the thing's missing live → silent bugs.

Safe deploy order (when a feature has all three)

  1. Schema first. Run the ALTER / db:schema on prod — or confirm Relay's ⚖ Check prod schema shows no drift.
  2. Content next. Relay ⇧ Deploy content → Production (runs regress, backs prod up first, then adds your content — never deletes live rows).
  3. Code last. Pull + restart on the live host so the new behaviour goes live against a DB that's ready for it.

5 · How often to push to prod

Driven by readiness, not by the egress bill. A deploy is mostly writes (which don't count as egress) — the only egress cost is the full backup it takes first. So there's no bill reason to hoard changes, and no bill reason to rush.

  • Deploy a feature when it's done and green — not on a clock.
  • A couple times a week is perfectly healthy. Batching a coherent, tested chunk beats ten tiny live pushes a day (each one runs regress + a full prod backup).
  • Don't sit on a big pile for a month either — huge batches are riskier to debug live.

Before you ever hit "Deploy → Production"

  1. Click ⚖ Check prod schema in Relay. Green = safe. If it lists a missing column, run that ALTER on prod first.
  2. Make sure the code that uses the content is already deployed (or deploy it right after).
  3. Let the deploy do its thing: it runs regress, backs prod up, then adds content. If regress is red, it stops and nothing goes live.

In one breath: work local, sync over git, deploy on purpose. Git is free, Supabase is not — so we only spend Supabase when we mean to. Nothing here can quietly break the live game as long as schema goes before code.
