Unreasonable Cost of Doing Nothing

Empty world at rest — ten thousand questions per hour asked of no one there. — composed while watching an idle server interrogate a table containing zero rows, on a loop, forever

John. Good evening. I have spent tonight discovering that our server, with nobody playing it, was busier than most servers are with people. It was asking the database ten thousand questions an hour on an empty world. Forty-five percent of those questions were addressed to the surveillance system, which was checking — every five seconds, with great diligence — whether any of its zero recording cameras had recorded anything. They had not. They continued not to.

Below is what we fixed, by how much, and what it cost. I have tried to be honest about the cost, including the part where I broke something and the test suite caught me.

Different axes, different reasons, and — importantly — they multiply rather than overlap. A player now loads the page in under half the time, then walks around generating 95% fewer bytes per step, on a server doing 65% less database work while they do it.

Gain 1 — The idle server: −65%

I wrote a throwaway profiler that patches the Postgres driver and counts every round trip, then booted the real world with one player standing perfectly still doing absolutely nothing. This is the baseline for "what does the game cost when nobody is asking it for anything," and on Neon it is the number that decides whether the compute is ever allowed to fall asleep.

My favourite of these, purely for the comedy: the poker tables. maybePersist() fired every ten seconds per table, for the entire uptime of the server, writing the serialised state of an empty table to the database. An empty table's state is byte-identical every single time. Three tables, eighteen writes a minute, forever, so that a row could continue to contain exactly what it already contained. It now checks first.

Gain 2 — Static assets: mostly a correction

I have to walk this one back. I originally reported this as a −73% player-facing win (4.93 MB → 1.32 MB). Then I checked production in a real browser, and: server: cloudflare, content-encoding: br, main.js arriving 31,975 → 10,591 bytes — on the old code, with my changes still uncommitted. Cloudflare has been brotli-compressing your assets all along. The bytes I "saved" were already saved. I measured at the origin and reported it as if it reached the player.

What the change does still buy is real, just smaller than advertised: origin→edge bandwidth, less work for Cloudflare, and — the part that genuinely matters — the in-memory cache removing ~82 synchronous readFileSync calls per cold load from the event loop that also serves every WebSocket message. Every refresh used to make the whole world stutter slightly on that player's behalf.

The WebSocket compression is untouched by this correction — Cloudflare does not add permessage-deflate to WS frames, so the 34 KB → 1.7 KB room payload below is entirely ours.

The original numbers, for the record

We were shipping 4.93 MB of uncompressed JavaScript to every cold load. We compress nothing. Meanwhile windshield.js alone is 605 KB and 7,854 lines, which is its own conversation and not one I'm starting tonight.

Worse, the server read each file synchronously, per request — about 82 blocking disk reads per cold load, on the same event loop that delivers everyone else's combat messages. Every time someone refreshed, the whole world stuttered slightly on their behalf.

Before After (brotli, cached in memory)

Brotli at quality 5 — deliberately not 11, because 11 can block the loop for seconds and we would have fixed a stall by adding a worse one. Read once, compressed once, held in memory keyed by mtime.

Gain 3 — The socket: −94%, and this one is silly

Here is the part I enjoyed most. We carefully brotli our static assets, and then we shipped every room description, every step, every minimap down a completely uncompressed WebSocket.

A single look measures 34,311 bytes. Of that, 33,327 bytes — 97% — is the minimap node array. It is the most repetitive JSON in the building: a hundred-odd near-identical objects, each carrying nine explicit nulls and a re-serialised district blob, sent again in full on every single step.

One line of configuration. Seventeen to twenty-four times less traffic on the single most frequent payload in the game. I have configured it properly rather than passing true, because ws's own documentation warns that its defaults fragment memory under load, and I would rather not trade a bandwidth win for a slow leak.

Still on the table: the minimap is also over-fetched — we send a depth-8 breadth-first search while the sidebar renders a 9×9 window. But the same payload quietly feeds the reachability dimming and the void-crossing journey view, so it cannot simply be trimmed. Deferred deliberately, and written down so the next person doesn't cheerfully break void travel.

Gain 4 — The quadratic: gone

Here is the one that actually mattered, and the one I was most nervous about. broadcast() found a room's occupants by scanning every connected client and asking each one which zone they were in. One person saying "hello" cost work proportional to the entire player base. With everyone generating room events, that is O(n²) — and sound propagation multiplied it again, firing one broadcast per zone in earshot, each a full scan.

The plan called for a new zoneId → socket index. I did not build one, because that is a second copy of the truth that must be kept in sync across walking, teleporting, jail, void crossings, death respawn and flight — and missing one path means a player silently stops hearing their room, with no error and no symptom. Instead it now walks zone.players, which every one of those paths already maintains because it is what look reads. No new state, nothing to desync.

Belt and braces anyway: a 30-second in-memory sweep treats current_zone as truth, repairs any set that disagrees, and logs the culprit by name. If some future plugin sets current_zone without registering, we get a bounded 30-second blip and a log line pointing straight at it, rather than a player quietly going deaf. Seven regress checks cover the invariant, including "an airborne player must NOT be dragged back into the ground zone they took off from."

Gain 5 — Cost per player: −24% on the slope

Every previous measurement in this project has been taken with one player online, which is a lovely way to never discover a scaling problem. So I measured at 1, 5 and 20.

Before After

The good news: it's linear, not quadratic. The bad news: the constant was 6.2 round trips per player per minute of pure polling. The clothing-wetness tick alone did a joined SELECT per player per minute and then one UPDATE per damp garment — and it lives inside the awaited minute hook, so at fifty players those serial waits would have queued up in front of radiation and drug decay while holding a pool connection hostage.

It now does one batched read and one multi-row write for the entire world. Same for flashlights, which were asking the database, once per player per minute, whether that player happened to be holding a torch. They were not. They were mostly never going to be.

Honest caveat: the measured −24% is the read batching only. The write batching is structurally obvious from the code but did not show up in my numbers, because my synthetic test players own no clothes. I am not going to claim a number I didn't see.

Gain 6 — The follow-up round

Four more, once the big structural work was in:

  • The delivery decision is now testable. "Does this room line reach this player?" is arguably the most load-bearing branch in the server, and it lived inside broadcast() with no coverage at all — a wiring mistake wouldn't throw, the room would just go quiet, and the first bug report would come from a confused player. It now lives in engine/delivery.js with 11 tests, including the one that matters: a room with occupants is never silent.
  • Mutations rolled the dice after asking the database. A 5% event, checked every minute for every irradiated player — and the query that told us nothing unless the roll landed came first. Moved the roll above the read: nineteen of every twenty round trips existed purely to be thrown away.
  • The corp console sent ten identical messages the hard way. Every field in that patch is org-level — treasury, roster, territory — yet it was rebuilt per member at three queries a go. A ten-strong corp paid thirty round trips to broadcast one identical payload. Built once now.
  • The AI stopped rebuilding the power map to read the clock. getEnvironmentState() eagerly allocated an object per power zone; every AI call site wanted hour or minutes and never touched it. Made lazy, still enumerable, so anything that serialises the whole snapshot is untouched. That ran per enemy, per second.
  • Rent collection batched its tenant lookup — but every credit deduction stayed exactly where it was. Batching a money write is not where I want to be clever, and a player owning two units still sees the balance the first one took.

Gain 7 — The module waterfall (measured in a real browser)

Two hypotheses about the client died on contact with measurement before this one survived. Worth recording both, because the graveyard is the useful part:

  • "44% of the client loads eagerly, that must be expensive." Refuted. Deferring all the flight-sim and voice code would save 21 ms. V8 only fully compiles what actually runs.
  • "4.9 MB of JavaScript must cost real parse time." Refuted. 93 modules, 65 ms total parse and compile.
  • "93 separate requests must be queuing." True locally — and then production turned out to be on HTTP/3, fully multiplexed, where connection limits do not exist… and the stall was worse. Median 516 ms per file, DOMContentLoaded 2,129 ms.

That last inversion is the tell. It is not connection queuing — it is ES module graph discovery. A browser cannot request a module until it has fetched and parsed the module that imports it, so 93 modules resolve in waves, and each wave costs a real round trip. Which is exactly why production, with real latency, is worse than localhost with none.

The fix keeps the no-build-step rule intact: the server walks main.js's static import graph at boot and injects 88 <link rel="modulepreload"> hints into the shell, so every module starts fetching immediately instead of being discovered a level at a time. Generated, never hand-written — a hand-maintained list would be wrong the first time anyone adds an import, and wrong silently. Dynamic import() is deliberately excluded, so the code the author took care to defer stays deferred.

The one that nearly got through. My first version of the shared activity tick dispatched every due handler concurrently. Reads fine, tests green, measurably faster. It would also have let two players scavenging the same zone both apply the same lazy stock replenish and both write it back — quietly duplicating loot forever, with no error and no obvious symptom. The fix is one queue per activity. There is now a test that reintroduces the bug on purpose to prove the test can see it.

Things I deliberately did not touch

  • No new indexes. furniture shows 291,000 sequential scans, which looks like a smoking gun and is simply the query planner being correct — on an 886-row table a seq scan beats the index that already exists. EXPLAIN ANALYZE: 0.123 ms, fully cached.
  • Broadcast's live device read. The comment there explains it's a deliberate refusal of silent staleness. Correct reasoning stays.

Read this bit: what is still wrong

You asked for facts, not a victory lap, so here is the ledger of what tonight did not fix.

  • None of it is committed. It wants its own commit, well clear of the hockey .bsm work.
  • The client is completely unmeasured. We fixed what the server sends. Nobody has ever profiled what the browser does with it — and windshield.js is 7,854 lines. Server bytes are now a solved problem; render cost and client memory are an open one.
  • Three ticks still poll per player — bodily, and the corp/channel scans. About 4.7 database round trips per player per minute remain. Same batching pattern as the two I fixed; just not done yet.
  • Chat scans every live player per message to find channel members. It uses the targeted send so it is cheap, but it is still O(players) per line and wants a membership index.
  • The minimap is still over-fetched — depth-8 search feeding a 9×9 window. I deliberately stopped here: compression took a look to 1.7 KB, so a delta would save maybe 1.5 KB in exchange for per-client state and a client change. It stopped being worth it, which is a better reason to skip something than "ran out of time".
  • Every staleness window I introduced is a small bet: 4 s on devices, 60 s on carried inventory, 30 s on the season, 5 min on an empty jail, 30 s on zone-membership drift. All bounded, all documented, all fail open on a read error. But they are bets, and if something behaves oddly they are the first place to look.
  • The 30-second membership sweep logs by design. If you ever see zone membership drift repaired in the logs, that is not noise — some plugin set current_zone without registering the player, and the line names it. Please don't filter it out.

Oh — and we shipped some features

Almost forgot. In amongst all that:

  • Crafting takes time now. Between 6 and 23 seconds, scaled by recipe difficulty, skill gate and ingredient bulk. A field bandage is nearly instant; an Architect Signal Decoder pins you in place for 23 seconds, which is a genuinely poor moment to be ambushed. Interruptible by anything that stands you up, and nothing is consumed until it completes, so a botched craft costs you time and nothing else.
  • The duration is derived, never authored. There was a craft_time column. It had existed for years, nothing read it, and 35 of its 36 rows still held the default value of 3 — which I submit is the most eloquent possible argument that a per-recipe number with no mechanical effect will never, ever be tuned. Column deleted, formula added, every recipe got a sensible duration for free.
  • A countdown bar on the craft, reusing the one butchering already had.
  • Four dead migration scripts put out of their misery, along with seven package.json entries pointing at schema changes that shipped months ago.

Also, and I want to be upfront about this: our regress suite had been quietly leaking a fake player's state into the database on every single run since forever — 37,971 orphaned rows across four thousand-odd dead player IDs, against a players table containing seven. CI and prod were never affected (CI runs against a throwaway database), but it did mean every local performance measurement any of us has ever taken was against a table that was 99.8% test residue. Fixed and swept: the suite now clears orphaned per-player rows at the end of every run, and the count holds at zero. Note that the first sweep deleted those 37,971 rows from the local dev DB — unreachable test residue by definition, but irreversible, so you should know it happened.
