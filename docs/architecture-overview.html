A structural tour of THOMAS, and of the one game running on it

2026-09-10  ·  branch main  ·  2,627 commits  ·  every figure below counted from the tree on the day

One engine, one game — the seam between them is drawn so a second can fit. — the whole architecture in seventeen syllables, and the only rule that has consistently paid for itself

Architect MUD is a post-singularity browser MUD in the HellMOO tradition: text-driven, real-time, brutal and funny. Underneath it sits a Node server talking raw WebSockets to vanilla JavaScript, with PostgreSQL as the only source of truth. There's no build step, no ORM and no framework — three absences that are load-bearing rather than incidental, and this document is largely about why.

Everything here was counted from the working tree on 2026-09-10 rather than quoted from a doc header. That distinction matters more than it sounds: this project has already shipped a lint rule specifically because five finished systems were reported as outstanding work, every error traced to a status line nobody updated.

The last two are the ones worth staring at together. A codebase of this size with four runtime dependencies and no dev dependencies at all — pg, ws, dotenv and a mail SDK — is unusual enough to be a deliberate position, and the 9,336-assertion suite is what makes that position survivable. You can't lean on a framework's guarantees if you haven't got a framework, so the guarantees are written down as tests instead.

Four names, nested

The most common orientation error here is assuming "Architect" names the whole thing. It doesn't. The platform and the game have separate names, and two of the subsystems have their own.

THOMAS — the platform

The Hypermedia Online Multiplayer Adventure System. The client and the engine: client/, server/engine/, the dev panel, the plugin loader, the CODEX pipeline. With modification — through the dev panel, which is the surface built for exactly that — somebody could stand up a different MUD on it.

GLASS — the renderer

Geometry, Lights, Aircraft, Streets & Structures. The 3D renderer, seen through exactly two windows: a cockpit canopy and a truck windscreen. Historically a CPU painter's algorithm on a plain 2D canvas; since 2026-09-09 the world draws in WebGL2 by default with the canvas retained as an overlay and a fallback.

SIREN — the synthesizer  /  ORACLE — the voice

Sources, Index, Resonance, Envelopes & Noise, and Orthography, Resonance, Accent, Cadence, Lexicon & Emphasis. A 32-voice FM synth with a tracker player and generated-IR reverb, and a four-formant speech synth over a 27,000-word lexicon. They share a file, some buses and a noise buffer — and nothing else. ORACLE never calls SIREN's layer builder, so an FM feature added to the synth does not reach the voice.

Architect — the game

Coldwater, the Basin, the orders, the prose. It lives in Postgres and under content/. One game, running on the platform above it.

Grepping for these names will mislead you. "THOMAS" appears in the codebase exactly once, in the dev panel's boot splash, where it reads as if it names the dev panel. It doesn't — it names the platform the splash is booting. SIREN and ORACLE appear only in file headers, and "siren" is already a domain noun here (the emergency siren, the dive siren, the cockpit warnings) with around 26 hits that have nothing to do with audio. These name systems; nothing in the code is called any of them.

How it fits together

One diagram, four flows. The thing to look for is the convergence: player commands come down from the top, world content comes up from the bottom, and both end at the same place — a set of plain JavaScript Maps held in server memory. That hub is what makes the hot paths affordable, and it's also where the subtle bugs live, because RAM and Postgres each believe they're authoritative about something.

player command path durable write coalesced write content deploy dev & authoring

Two details in that picture are worth more than the boxes. The left-hand return path is the whole reason the hub exists: room output walks zone.players — a set the movement, jail, death, flight and void-crossing paths all already maintain — rather than scanning every connected socket to ask who's nearby. And the right-hand return path is the only arrow that runs at boot and never again, which is what makes 41,495 content files affordable to serve.

The one rule

No one touches code to create content. The codebase is the engine; the world is data. Writers and designers work through a browser-based dev panel, and publishing a zone edit never requires a deploy.

Stated that way it sounds like tidiness. It isn't, and the reason is the name stack above: every piece of Coldwater that ends up hardcoded in an engine or client file is a thing a second game would have to unpick. That's what gives the rule teeth. It isn't a preference about file organisation, it's the thing that keeps THOMAS reusable, and each violation has a measurable future cost.

The split shows up in the line counts. Of 479,575 lines of JavaScript, none of it is world content — the world is 41,495 JSON files and 149 Postgres tables sitting entirely outside the code.

No startup migrations

The server touches neither schema nor content on boot. Both are deliberate acts:

  • Schema is one exported string — SCHEMA_SQL in server/models/schema.js, 3,234 lines of idempotent DDL covering 149 tables. Applied locally on demand; applied to production by CI.
  • Content lives in git as one JSON file per entity. A push to main is the deploy: CI backs production up, applies schema ahead of content, and refuses to proceed on a red regress.
  • One-shot scripts against production are reserved for what the deploy genuinely can't do, which is narrower than it looks — the import is an upsert that replaces whole columns, so editing a content file is enough to remove a JSON key.

The old boot-time migrate() was removed precisely because content-rewriting code firing on every restart made local development unpredictable. Boot stays dumb on purpose, and the same reasoning is why the regression suite is never wired into production startup.

How a command travels

A player types something. Five stages decide what happens, in this order, and the order is the architecture — plugins beat engine builtins, which is what lets a plugin take ownership of a verb the engine also defines without either side knowing about the other.

1SIFT interceptTarget resolution and selection state. Runs before all routing, and owns bare numbers — so answering "which rusty pipe?" with "2" can't be mistaken for a command.
2Input matchersPattern matches on the whole line rather than a verb. This is how pspsps calls a cat, without call and summon being stolen from the poker table.
3Plugin commands623 verbs across 95 plugins, registered from plugin.json manifests. A verb not listed in the manifest does not exist, however complete the handler is.
4Specialized actionsVerb-first, tag-gated. open means something different to a door, a container and a letter, and none of those three implementations knows about the others.
5Engine builtinsThe floor. Movement, look, inventory, say — the verbs that must work in a world with every plugin disabled.

Because stage 3 precedes stage 5, an engine builtin whose verb a plugin has claimed is dead code that still looks alive. That's common enough to be the first thing the contributor docs tell you to check before editing any command handler.

Plugins: a long tail with a whale in it

137 plugins, of which 95 declare player verbs and 42 declare none at all — those are pure hook subscribers, adding behaviour to flows they never expose a command for. The distribution is lopsided in a way that's worth knowing before you go looking for a system:

player verbs declared, top 10 of 95

The median plugin declares two verbs. The flight plugin declares 101. That isn't a defect — flight carries aircraft, airfields, hazards, contracts, air combat and hangars, and it earns the count — but it does mean "look in the plugin with the obvious name" works far better for small systems than large ones.

Plugins communicate through four seams, none of which require them to import each other:

SeamShapeUsed for
ActionsregisterAction / dispatchActionThe canonical mutation path. Dispatched by name, so demolition can charge a crime without importing surveillance
HooksfireHook — 40 named hooksGather and veto points. Some collect contributions from every listener; some keep the last non-undefined answer
EventsIn-process bus, on / emitFire-and-forget notification. One subscriber in the quests plugin yields a whole objective type for free
RegistriesMove gates, lock types, status effects, specialized actionsTyped extension points — 47 move gates and 45 status effects registered across the tree

The hook contract is where the subtle bugs live. The two shapes look identical at the call site and behave completely differently: a gather hook collects from everyone, while fireHook hands every handler the same original arguments and keeps the last non-undefined result. A second opinion on a last-wins hook doesn't refine the first one, it replaces it — which is why the Blind Fighting discipline deliberately isn't a visibility.perceive contributor, despite its own design document prescribing exactly that. Returning undefined when you have no opinion doesn't rescue it, because in a dark room it has one.

Where data lives, and when it's written

Production Postgres is remote, so the cost that matters is never query complexity — it's round-trip count. Two tier systems govern this, one per direction, and the rule is that you pick a field's tier before writing the code.

Persistence tiers — the write side

TierMeaningPolicyOn crash
DurableMust survive any deathWrite through at the mutation siteIntact
CheckpointMust survive a clean restartWrite at logout and coarse boundaries — never per tickLoses ≤ one interval, benignly
DerivedRecomputed or irrelevant at bootNever written from ticks or transitsRebuilt

Money and inventory are durable. Position, combat HP and the survival resources are coalesced: the mutation site sets a dirty flag, and a low-frequency flush persists every dirty player in one UPDATE … FROM (VALUES …). That decouples round-trip count from player count multiplied by action rate on exactly the paths that scale worst — a busy zone of 200 players costs the same number of writes as a quiet one. The payload grows; the round trips don't.

The cost of that pattern is discipline, and a violation fails silently. There's no error when a new damage source forgets to set _resDirty — the damage simply never persists. Five invariants hold it together, and the most easily broken is ordering: the resource flush is deliberately the last statement in the combat tick, so anything added after it won't be seen until the next one.

Read tiers — the other direction

Six tiers, from "boot-loaded into a Map" through "event-bust plus TTL" down to "query fresh, because the writers are uncoordinated". The decision procedure is one sentence, and it's the most quoted line in the architecture doc:

A cache is only as safe as its write funnel. Before caching a table, grep every INSERT, UPDATE and DELETE against it. If the writers are scattered and can't maintain the cache, either build the funnel first or stay on "query fresh" — a stale cache that misrenders lights or sells from a phantom shelf is strictly worse than a round trip.

furniture and npcs are the two tables that had to earn their funnels before they could be cached: around 40 scattered furniture writers were routed through three helpers first. Bulk writers hand their SQL to a wrapper that appends RETURNING and re-caches exactly the rows Postgres says it touched, because hand-writing a JavaScript mirror of a WHERE clause creates a second source of truth for the predicate, and drift between the two stales the cache invisibly.

GLASS: a renderer that moved to the GPU without being rewritten

The flight sim and the truck cab share one renderer. Until 2026-09-09 it was a CPU painter's algorithm on a 2D canvas, with faces queued and flushed back-to-front because there's no depth buffer to sort them. It now composites in WebGL2 by default — and the interesting part is what didn't change.

The 173 building models are still hand-written drawing code. They weren't ported. Instead they record themselves: the same functions that draw a building emit their geometry into a sink, so one set of model code now feeds the GPU mesh, distance LOD, occlusion culling, ground shadows, per-point collision and the intro cinematic's skyline. An authored model plugs in at one function and every one of those consumers reads it with no change of their own.

SurfaceWhere it draws nowWhy it moved
Building massGPU meshTruck frame 5.7 → 2.4 ms; aircraft 21.8 → 13.6 ms
The groundFragment shaderWas the largest fixed cost in the frame: 32.9 → 1.3 ms in a city, 65.4 → 0.6 over open sea

Every failure path hands the world back: no WebGL2, a lost context, a shader that won't compile, a texture page the device can't hold, a pass that returns nothing, and a pass that throws all set the flag to 0 and finish the frame in 2D. That fallback is what makes the default defensible.

Honest caveat, and it's the same one every time. All of those numbers come from one machine with a discrete NVIDIA card. "Falls back correctly" is not "is fast on an integrated GPU", and no other hardware has been tested. Treat the millisecond figures as a direction, not a guarantee.

The other lesson from that work is methodological, and it generalises past rendering. Three successive attempts to answer "what should we port next" produced confident wrong answers: a city built from hand-picked models picked its own conclusion, a loose adaptive resolution dial read as though it were the renderer, and a call count turned out not to be a millisecond — a function responsible for 492 of 1,800 canvas calls measured at 0 ms. The harness now reports a spread, because the same seat once gave one pass an 8.4 ms cost and a 6.7 ms saving on consecutive runs. A difference inside the spread is not a finding.

The chain covers more ground than "does the code work":

  • Every client file parses. There's no build step, so before this nothing between an editor and a player's browser ever parsed them. The failure it exists for is a backtick inside an HTML comment inside a template literal, which once ended a string mid-sentence and killed the entire client boot in production.
  • Every named import resolves to a real export — checked against the commit being pushed, not the working tree. That distinction is the whole point: a commit once shipped an import whose export existed only in an uncommitted file, so the local suite passed 8,988/8,988 while CI couldn't load the plugin at all.
  • Every building model executes at night and day, at both entrance facings, against a DOM stub. Before this, the only thing that ever ran a model was a player flying past that particular building.
  • Every doc link resolves, every plugin verb is documented, and a status header saying "not built" above a body full of completion markers is a hard failure.
  • Every content file is linted for runtime columns that shouldn't be in git.

Three ways this gate lies to you, all discovered the hard way. A run that was killed prints no trailing N/N passed line — absence of that line means the suite didn't finish, which is a different problem from a failing test. Piping the run to tail reports tail's exit status, so a red suite comes back 0 and any wrapper watching the exit code calls it green. And starting a second suite kills the first, because the orphan sweep that runs first includes the suite itself in its process filter.

Read this bit: what's still awkward

An architecture document that only describes intentions is the failure mode this project already has a lint rule for. So, the ledger.

  • One file is 26,256 lines. windshield.js owns the scene, the 173 model arms, LOD, the occluder field and collision. It was 7,854 lines in July. It has real automated coverage now, which it didn't then, but size alone makes it the hardest file in the tree to change safely.
  • The renderer's numbers come from one GPU. Stated above and repeated here, because it's the claim most likely to be quoted without its caveat.
  • The regression suite never boots the environment. No initEnvironment, so the power grid and weather simulation are uncovered. A green suite proves nothing about either — and power is per-zone across 17,239 zones, so that's a wide blind spot.
  • Plugin size is unevenly distributed against plugin docs. 133 of 137 plugins have a README, but a 101-verb plugin and a 2-verb plugin get the same structural treatment, and the large ones are correspondingly harder to navigate.
  • Eleven plugins have no regress.js. The convention is that a plugin ships its own suite; most do, and the gap is not currently tracked anywhere that would fail a push.
  • The dev panel is the platform's reuse story and is barely exercised by tests. The claim that somebody could build a second MUD on THOMAS rests on the dev panel being sufficient, and nothing verifies that end to end.
  • Every cache is a bet with a stated window. They're bounded, documented, and they fail open on a read error — but if something behaves oddly, they're the first place to look, and the list of them is longer than it was a year ago.
No framework beneath — nine thousand assertions hold the floor up instead.
