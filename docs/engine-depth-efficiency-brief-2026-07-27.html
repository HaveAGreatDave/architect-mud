Depth without
cost: where the
two disciplines meet

Two things this project does unusually well, measured rather than asserted. The systems go deeper than their surface suggests, and the engine pays almost nothing to run them — because the depth was put in memory and the database was told to stay out of the way.

I · The read-tier discipline measured

The single most consequential rule in this codebase is that every content table declares where it is read from before anything is allowed to read it. Not a convention — a registry entry, validated by regress.

Content tables in the registry 56
…carrying an explicit read tier 56 / 100% no content table in this repo is read from an undeclared tier
Loaded once at boot, served from RAM forever 36
Cold — queried on demand, never boot-loaded 12
Fresh / TTL — deliberately re-read 6
Annotated dead — zero runtime readers, on purpose 2

The 36 boot-tier tables are why the world is a set of in-memory Maps rather than a query surface. The 12 cold ones are the counterweight and the more interesting decision: books is cold and never boot-loaded, which is the entire reason a library of eight full novels is affordable to ship at all. A table's tier is a budget, and the budget is written down.

Why this is the load-bearing rule. Production Postgres is remote. Latency lives in round-trip count, not query cost — so a feature that adds one awaited query to a per-move path costs more than a feature that adds a thousand rows to a boot-loaded table. Tiering makes that tradeoff explicit at design time instead of discoverable at 3am.

II · Sync by contract the hot path

Five substrates in this engine are synchronous and query-free by contract — not "currently fast", but structurally incapable of a round trip, because a `await` in them would be a bug the contract forbids.

condition.js0 queries Hunger, thirst, temperature and fatigue → the stats you act with. Sits under skillStatBonus, so it reaches every skill check in the game without a call site knowing it exists.
hygiene.js0 queries Filth on a body. Called from the smell pass and from NPC reaction paths — both places where a query would be per-look and per-tick.
zone-filth.js0 queries Filth on a floor. RAM is the source of truth for stains; the 7-day cadence is stateless, derived from the game date, so a restart can't reset the city's mess.
relations.js2 (hydrate + flush) What an NPC remembers about you. Hydrated once at login, read from memory thereafter — getRelation is sync by contract. Time-decay is lazy with no tick at all.
durability.js3 (flush only) Gear wearing out. wear() is sync by contract because it is called from the combat swing; accrual is in memory, flushed coalesced.

The measurable consequence is on the two hottest paths in the game. A combat swing and a player move — the things that happen thousands of times an hour — carry almost no awaited database work between them:

combat.js — the per-swing path 2 awaited queries
movement.js — the per-move path 3 awaited queries both files are thousands of lines; the queries are flushes, not reads
Coalescing flush functions across the engine 6 flushDirtyResources · flushWear · flushAllWear · flushRelations · flushAllRelations · flushDirtyPositions
Idle-gate call sites (hasActivePlayers) 17
Scheduled ticks routed through scheduler.js 69 one clock, not 69 setIntervals racing each other
The pattern generalises. Every one of those five substrates followed the same route: put the state in the live player or zone object, make the read synchronous, accrue in memory, and flush coalesced on a boundary that already exists (logout, tick, zone change). None of them added a tick of their own. Relationships added zero — decay is computed lazily from a timestamp when you next look.

III · Systems depth the vertical

Depth here means a system that keeps rewarding attention after you understand it. The proxy is decomposition: a system with one file has one idea, and a system with thirteen has been taken seriously.

Cooking as the worked example

Thirteen modules, each a distinct question the system asks about a single piece of food: profiles (what kind of thing is this), prep (what did you do before heat), portions (how big is it), cook (the clock), fond (what the pan kept), quality (how did it go), taste (what it's like to eat), knowledge (what you've learned), dishes, interact, help, config, index.

Ingredient profiles (dense meat, soft vegetable, …)12
Quality bands from poor to masterful9
Independent inputs to one dish's final score9 doneness · prep ceiling · vessel · heat tier · timing window · fond · skill margin · mince penalty · profile targets
Skills in the game, each governed by two stats23
Engine modules behind it all85
Engine hook fire sites — the plugin seam40

The tell for real depth is that the trades are reciprocal. Mincing cooks in a third of the time and permanently costs a quality band — fast food that can never be good food. Chopping buys speed and costs yield, and since today it follows m^(2/3) rather than mass, it buys less speed than it looks like it should. None of these are bonuses; each is a question with a wrong answer available.

Depth is cheap when it lives in RAM. Everything above — 12 profiles, 9 bands, 9 scoring inputs, a fond model — costs the database nothing. A cook session is state on a live object with a timestamp; the quality evaluation is arithmetic. This is the actual thesis of the codebase: simulation depth and query count are independent variables, and most engines conflate them.

The last row is the one worth dwelling on, because it is the discipline working correctly rather than failing. Both tables are hot and both would benefit from a cache; both were left uncached because someone grepped the writers first and found too many. Choosing not to optimise, and writing down why, is the same skill as optimising.

V · The through-line

These two hallmarks are not independent. They are the same decision seen from two angles.

A system gets deep when adding another layer is cheap. Adding another layer is cheap when the layer costs no round trip. So the read-tier discipline isn't a performance concern that sits beside the simulation work — it is the thing that makes the simulation work affordable. Relationships could add a six-rung memory ladder for every NPC because it cost zero queries and zero ticks. Hygiene could add a contaminant table because hygieneOf is sync. Cooking could add a ninth scoring input because the eighth was free.

The failure mode this avoids is the common one: a game that is deep in design documents and shallow in play, because every interesting interaction turned out to cost a database call and got cut in review. Here the interesting interactions were made structurally free first, and the depth followed.

The rule, stated once: put the state where the read happens, make the read synchronous, accrue in memory, flush on a boundary that already exists, and write down which tier you chose. Every substrate in section II is that sentence applied to a different noun.
